● Creating a memo from the Home composer does not go through Store.CreateMemo
  (store/memo.go:185), even though that is the obvious name. It goes through
  Store.ApplyMemoMutation, which inserts the memo row, links its attachments and
  writes its relations in one database transaction. I read the files but
  changed nothing. The knowledge graph query returned mostly test files for this
  question, so the trace below comes from reading the source.

  2. The API call

  - Connect RPC: POST {origin}/memos.api.v1.MemoService/CreateMemo with a
    binary-protobuf CreateMemoRequest { memo }.
  - It is defined in proto/api/v1/memo_service.proto:22 as rpc CreateMemo. That
    file also maps a REST route, POST /api/v1/memos, through gRPC-gateway, but
    the web UI uses the Connect route.

  3. Backend routing (server/api/v1)

  1. server/api/v1/v1.go:227-242: Connect handlers are mounted on
     /memos.api.v1.* with interceptors that run in this order:
     NewMetadataInterceptor → NewLoggingInterceptor → NewRecoveryInterceptor →
     NewAuthInterceptor (authenticates the user).
  2. server/api/v1/connect_services.go:368, ConnectServiceHandler.CreateMemo:
     unwraps the request, calls the service and converts errors with
     convertGRPCError.

  4. Backend handler and helpers

  server/api/v1/memo_service.go:25, APIV1Service.CreateMemo, runs these in
  order:

  1. fetchCurrentUser (auth_service_session.go:269): returns Unauthenticated if
     there is no user.
  2. throttleAndCharge(ratelimit.ScopeWriteUser, …) (ratelimit.go:150): rate
     limiting.
  3. ValidateAndGenerateUID(request.MemoId) (resource_name.go:177).
  4. prepareMemoCreate (memo_create_helpers.go:34) checks and builds the memo
     without writing anything:
     - validateCreateMemoVisibility (memo_service_converter.go:411)
     - resolveSpaceForMemoPlacement (memo_access.go:134), only when a space is
       set; SPACE visibility requires one
     - custom create/update timestamps are applied if provided
     - getContentLengthLimit (memo_service.go:563) and the length check
     - memopayload.RebuildMemoPayload (core/memopayload/runner.go:74): parses
       the markdown into the payload; location is then set on it
     - prepareMemoAttachments (memo_attachment_service.go:70)
     - resolveMemoAttachmentReferences (memo_attachment_service.go:360)
     - prepareMemoRelations (memo_relation_service.go:55)
  5. createMemoWithMutation (memo_attachment_service.go:156): checks that the
     creator is the current user, builds the attachment bindings with
     buildMemoAttachmentMutationBindings, and calls
     s.Store.ApplyMemoMutation(&store.MemoMutation{MemoCreate: …}). On failure,
     mapMemoCreateError (memo_create_helpers.go:15) turns a UNIQUE/duplicate
     error into AlreadyExists.
  6. After the write:
     - Store.ListAttachments and loadMemoRelations
     - convertMemoFromStore (memo_service_converter.go:26): builds the v1pb.Memo
       that is returned
     - DispatchMemoCreatedWebhook (memo_service_webhooks.go:19): best effort
     - SSEHub.publishMemoChanged(): notifies live clients
     - dispatchMemoMentionNotificationsBestEffort (memo_mention_helpers.go:169)

  5. Store and database write

  1. store/memo_attachment.go:90, Store.ApplyMemoMutation: checks that a create
     mutation doesn't also update or remove anything, calls validateMemoCreate
     (store/memo.go:212), checks the write policy, attachment bindings and
     reference relations, then calls s.driver.ApplyMemoMutation (line 165). The
     driver interface is at store/driver.go:29.
  2. The driver implementation depends on the database. For SQLite,
     store/db/sqlite/memo_attachment.go:15, DB.ApplyMemoMutation, does the
     following:
     - BEGIN IMMEDIATE
     - validateSQLiteMemoRelationEndpoints
     - validateSQLiteMemoCreate (store/db/sqlite/memo.go:71), which checks space
       membership through validateSQLiteMemoSpaceMember (line 97)
     - insertSQLiteMemo (store/db/sqlite/memo.go:34): INSERT INTO memo (uid, 
       creator_id, content, visibility, payload, space_id[, created_ts, 
       updated_ts]) … RETURNING id, created_ts, updated_ts, row_status. This is 
       the row write.
     - Re-reads the memo row to confirm creator and content
     - Binds each attachment with UPDATE attachment SET memo_id = ? … and checks
       the attachments that the memo content references
     - replaceMemoReferenceRelations (line 168) writes the memo_relation rows
     - COMMIT
  3. MySQL and Postgres follow the same pattern:
     - store/db/mysql/memo_attachment.go:15 → insertMySQLMemo
       (store/db/mysql/memo.go:36)
     - store/db/postgres/memo_attachment.go:15 → insertPostgresMemo
       (store/db/postgres/memo.go:35)

  Comments take a similar path: the frontend calls createMemoComment, and the
  backend passes CommentContextMemoID, so the transaction also calls
  authorizeSQLiteMemoComment and insertSQLiteMemoCommentRelation.
